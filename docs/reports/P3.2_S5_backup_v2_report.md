## 3. 导入校验顺序（严格按设计 §11.3）

| 步  | 动作                                            | 失败提示                                              |
| --- | ----------------------------------------------- | ----------------------------------------------------- |
| 1   | 非空、JSON 可解析、顶层对象                     | 「不是有效的 JSON」/「顶层应为 JSON 对象」            |
| 2   | `format` 匹配                                   | 「format 标识不匹配」                                 |
| 3   | `formatVersion == 1`                            | 「格式版本 vN 不受支持」                              |
| 4   | 读 `schemaVersion`，必须是 1 或 2               | 「缺少有效的 schemaVersion」/「不支持的备份数据版本」 |
| 5   | `schemaVersion > 2` 拒绝                        | 「高于当前应用支持的 v2」                             |
| 6   | 按版本选 schema 做 zod 校验                     | 「字段校验失败 —— 路径：原因」                        |
| 7   | v2 声明必须带全 11 数组                         | 「缺少数据表：…」                                     |
| 8   | **checksum 对原始 `data` 重算**                 | 「校验和不匹配…未写入任何数据」                       |
| 9   | 归一化：补 3 数组、`tasks[].deletedAt ??= null` | 不报错（v1 专用）                                     |
| 10  | `counts` 与归一化数据逐表比对（v1 缺 3 键跳过） | 「元信息与内容不一致：X 声明 N 条，实际 M 条」        |
| 11  | 引用完整性 + 修订链                             | 「悬空引用 —— …」/「修订链断裂」                      |

关键修正：**checksum 在归一化之前**。v1 备份的校验和是对 8 个数组算的，若先补 `[]`/`deletedAt` 再比对，任何合法 v1 备份都会被判为「已损坏」——这是 S5 必须修掉的实际缺陷。

## 4. 引用完整性（新增 3 类）

在原 8 表规则（项目/父任务/标签/计划任务/日志关联/报告周期）之外，新增：

1. `longTasks[].tags ⊆ tags`；
2. `longTaskRuleVersions[].taskId ∈ longTasks`；
3. `longTaskExceptions[]`：
   - `taskId ∈ longTasks`；
   - 同一 `(taskId, occurrenceDate)` 的 `revision` 必须为 `1..n` 连续；
   - `revision = 1` 的 `previousRevisionId` 必须为 `null`；
   - `revision > 1` 必须指向同组 `revision - 1` 的那条记录 id。

链断裂一律拒绝恢复，不静默丢弃记录。

## 5. 覆盖恢复

单事务覆盖 11 表：`clear()` → `bulkAdd`（`settings`/`meta` 用 `bulkPut`）→ 写 `lastImportedAt`；任一步失败整体回滚，库保持导入前状态。恢复**保留原 `deletedAt`**（回收站任务不会因恢复而复活）。

## 8. 与设计的差异

| 项            | 设计             | 实施                               | 理由                                                                                     |
| ------------- | ---------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| v1 迁移实现   | 走 `migrateData` | 在 `inspectBackupText` 内归一化    | 设计 §11.3 第 7 步即「归一化」，DB 迁移与备份归一化是两件事，避免为备份扩充 `MIGRATIONS` |
| v2 缺数组检测 | zod 结构错误     | 解析后显式检查并给出「缺少数据表」 | zod union 会让「v1 分支」兼容 v2 形状，显式检查才能保证语义                              |
| `counts` 类型 | 全量 11 键       | 导入时允许 partial（v1 只有 8 键） | 兼容 v1                                                                                  |
| 诊断面板      | 未提及           | 计数扩到 11 表                     | `countsOf` 需要 11 键，属连带修复                                                        |

## 9. 未覆盖与风险

1. 导入 UI 仍是旧面板（`BackupCard`）：没有「自动先备份当前库」「含多少已删除长期任务」的摘要展示——属 S7。
2. 导入不校验 `longTasks.endCondition` 与 `endDate` 的业务互斥（结构层只校验类型）；脏数据进入库后由守卫在写入时拦截，但「导入即脏」不会被发现。
3. 大备份（万级任务 + 长期任务）内存与耗时未压测。
4. `countsOf` 现在要求 11 键；第三方脚本若按 8 键构造数据会编译失败（属预期收紧）。
5. v1 备份若含 `longTasks` 数组但 `schemaVersion=1`，会被当作 v2 数据导入（不丢数据）；未加显式拒绝。
