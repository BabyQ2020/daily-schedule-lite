## D. 删除语义

| 操作                                  | 写入范围                                     | `archivedAt` | `dailyPlans.taskIds` | `workLogs`               | 返回值                                              |
| ------------------------------------- | -------------------------------------------- | ------------ | -------------------- | ------------------------ | --------------------------------------------------- |
| 软删除 `softDeleteTasks`              | 仅 `tasks.deletedAt` + `updatedAt`           | 保留         | **保留**             | **不动**                 | 实际变更条数（幂等，重复为 0）                      |
| 恢复 `restoreDeletedTasks`            | 仅 `deletedAt=null` + `updatedAt`            | 保留         | 不动                 | 不动                     | 实际恢复条数（未删的不写）                          |
| 彻底删除 `purgeTasks` / `deleteTasks` | `tasks` 删除 + 计划摘除 + 日志置空（单事务） | —（行已删）  | 移除该 id            | `taskId=null` + 标题快照 | `{deleted, detachedLogs, updatedPlans}`（实际条数） |
| 归档 `archiveTasks`                   | `archivedAt` + `updatedAt`                   | 置时间       | 不动                 | 不动                     | 命中行数                                            |
| 取消归档 `restoreTasks`               | `archivedAt=null` + `updatedAt`              | 清空         | 不动                 | 不动                     | 命中行数                                            |

要点：

- `archivedAt` 与 `deletedAt` 完全独立，可同时非空；回收站查询 `deletion:'deleted'` 会返回「已归档且已删除」的记录。
- 软删除**不**级联，唯一清理入口是彻底删除；UI 占位（灰色「该任务已删除」）留给 S3。
- 彻底删除的标题快照使用删除前读到的标题，若日志已有快照则不覆盖。

## E. 事务原子性测试

注入方式：Dexie 表级 `hook('updating')`，在写入步骤**真实持久化过程中**抛错（不是非法输入触发的 `ValidationError`）；`finally` 中 `unsubscribe()`，避免污染其他用例。断言全部在事务结束后用新事务重新读取。

| 用例 | 注入点                                      | 预期                                                                                 | 实测 |
| ---- | ------------------------------------------- | ------------------------------------------------------------------------------------ | ---- |
| A    | `dailyPlans` 更新时抛错（tasks 已删除之后） | 整体回滚：tasks 存在、计划仍含 id、日志 `taskId` 不变                                | 通过 |
| B    | `workLogs` 更新时抛错（计划已更新之后）     | 三表回到事务前：tasks 存在、计划含 id、日志 `taskId` 与快照原样                      | 通过 |
| C    | 无注入                                      | tasks 记录不存在、计划不再引用、日志 `taskId=null`、快照为删除前标题、计数与实际一致 | 通过 |

补充：`purgeTasks(['missing', 有效 id])` 返回 `deleted: 1`，说明计数按实际删除行统计。

## F. updatedAt 测试

| 场景                                                 | 期望                     | 结果                              |
| ---------------------------------------------------- | ------------------------ | --------------------------------- |
| `now` 早于旧值                                       | `previous + 1ms`         | 通过（`09:00` → `10:00:00.001Z`） |
| `now` 等于旧值                                       | `previous + 1ms`         | 通过                              |
| `now` 晚于旧值                                       | 直接取 `now`             | 通过（`11:00`）                   |
| 同一毫秒连续两次 `updateTask`                        | 两次均严格递增           | 通过                              |
| 批量 `archiveTasks`/`restoreTasks`/`softDeleteTasks` | 每条相对自身旧值严格递增 | 通过                              |
| 非法 ISO 输入                                        | 抛错（不写库）           | 由 `ISO_TIMESTAMP_PATTERN` 保证   |

实现：`nextUpdatedAt(previous, now) = new Date(Math.max(Date.parse(now), Date.parse(previous) + 1))`，输出统一 `toISOString()`。所有 Task 写入点（create 除外，create 直接用创建时间）均已接入；S2.1/S2.2 的 LongTask 写入必须复用同一函数。

### H.3 需要关注的风险

1. **统计与备份目前绕过删除过滤**：`services/stats/*`、`services/backup.ts`、`services/exporters.ts` 直接读表，软删除任务仍会被统计/导出。当前没有 UI 入口创建软删除，故不影响现有页面；S3/S5 必须统一口径（建议在 service 层过滤 `deletedAt === null`）。
2. **删除过滤在内存完成**：`tasks.deletedAt` 有索引但当前未用于候选集裁剪（IDB 无 null 索引，回收站用 `deletedAt > ''`），10k 量级可接受；S5 性能阶段复核。
3. **`getTask` 返回软删除记录**：这是刻意保持的既有语义（编辑/回收站需要），调用方若要「活动任务」判定需自行检查 `deletedAt`。
4. **`updatedAt` 严格递增的副作用**：注入时钟早于记录时间时，结果会被抬高到「旧值+1ms」，属于预期行为，但报表排序会出现「未来时间」，仅影响测试注入场景。
