## 3. 统一判定：`aggregateIssues()`

诊断与写入共用同一个纯函数，避免「诊断说不健康、写入却放行」：

```ts
aggregateIssues({ task, versions, exceptions, today }): AggregateIssue[]
  = validateLongTask({ task, versions, today })      // A1–A10
  + validateExceptionChain(exceptions)               // E4–E8
  + 版本号连续性（A11，新增）
```

`validateLongTask` 只保证 versionNo 单调递增，无法发现 v1→v3 的断档；诊断要求「断链可见」，因此在聚合层补 A11。

## 4. 写入阻断

`assertAggregateHealthy()` 在事务内、拿到三表数据之后调用；失败抛 `ValidationError`：

> 该长期任务的数据存在一致性问题：<首条问题> 已阻止写入，请先导出备份并修复数据。

接入的 6 个写入口：`updateLongTaskInfo`、`appendLongTaskRuleVersion`、`appendLongTaskException`、`revokeLongTaskException`、`appendLongTaskLifecycleEvent`、`reopenLongTaskWithRuleVersion`。为读齐数据，`updateLongTaskInfo`、`appendLongTaskRuleVersion`、`appendLongTaskLifecycleEvent` 的事务表清单各扩到三张（`appendLongTaskRuleVersion` 另有既有的 `assertVersionChain` 先抛，文案更具体，属可接受差异）。

**不阻断**：`setLongTaskArchived`、`softDeleteLongTask`、`restoreLongTask`、`purgeLongTask`。理由：坏数据必须永远能被移走；如果删除也被挡住，用户只能改数据库才能自救。

## 5. `diagnoseLongTasks()`

只读事务扫描三表（含软删除任务）：

```ts
interface LongTaskDiagnosisReport {
  scannedAt: string;
  total: number;
  healthy: number;
  entries: { taskId; title; deleted; issues }[];
  orphanVersions: number; // taskId 不存在于 longTasks
  orphanExceptions: number;
  durationMs: number;
}
```

- 不修复、不写库、不阻断启动。
- 孤儿版本/例外不计入 `entries`（它们不属于任何聚合），单独计数。
- 每任务的问题按 `validateLongTask` + 例外链顺序输出，UI 直接展示 code 与文案。

## 9. 与冻结设计的差异

1. **阻断位置**：放在仓储层事务内，而不是 Service 或 UI。Service 只是转发，UI 无法保证所有入口；仓储层是唯一写入口。
2. **新增 A11**：`validateLongTask` 的 A8/A9 只覆盖顺序，不覆盖断档；诊断要求断链可见，故补连续性检查。
3. **孤儿不进入 `entries`**：设计只要求「扫描聚合」，孤儿没有聚合主体，单独计数更符合语义。
4. **诊断包含软删除任务**：回收站里的坏数据同样要能被发现与导出，否则恢复就会带病上线。

## 10. 未覆盖与剩余风险

- 不提供自动修复（设计明确要求）；修复仍需人工改库或后续专门工具。
- 诊断是全表扫描，万级长期任务时耗时会线性增长；当前无分页/流式，实测 1 任务 <5ms，规模上限未验证。
- `SettingsPage.test.tsx` 整文件较慢（约 40s），与本阶段无关。
- 坏聚合仍可被归档/软删/恢复，这是刻意保留的自救通道，需在文档中说明。
- 未做真实浏览器多标签并发验证（沿用 S2.2 的 `fake-indexeddb` 限制说明）。
