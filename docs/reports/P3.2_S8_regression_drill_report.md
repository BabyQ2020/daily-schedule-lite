## 3. 演练 A–D（fake-indexeddb 等价复刻）

### A. v1 八表升级到 v2 十一表

构造 v1 库：`tasks` 2 行、`projects`/`tags`/`dailyPlans`/`workLogs`/`reports`/`settings`/`meta` 各 1 行；用生产 `createDatabase()` 打开触发升级。

断言全过：

- 表名集合等于 11 张表的完整清单；
- 原 8 表行数与升级前**逐一相等**；
- `longTasks`、`longTaskRuleVersions`、`longTaskExceptions` 均为 0 行；
- 每行 `deletedAt === null`（无 `undefined`）；
- `deletedAt` 索引可查（`above('')` 为 0，同时用 `filter` 确认 2 行未删）；
- `status` 索引可查。

> 说明：IndexedDB 不索引 `null`，因此 `deletedAt` 索引只服务「回收站」类查询（`above('')`），未删行走全表过滤。这与设计 §10「`deletedAt > archivedAt`」的语义一致，已在测试注释中写明。

### B. 升级失败后仍可重试

用与生产同构的 v2 声明，但在 `upgrade` 中主动抛错：

- 打开被拒（`rejects.toThrow`）；
- 关闭后以 v1 声明重开：`verno === 1`、`tasks` 仍 2 行、无 `longTasks` 表；
- 再用生产 `createDatabase()` 打开：升级成功、`verno === 2`、`deletedAt` 全部回填为 `null`。

结论：IndexedDB 的版本变更在整个 `versionchange` 事务内原子完成，失败不会留下半升级状态（C5 语义）。

### C. 用 v1 备份回滚到升级前数据

- 从升级前的 v1 快照构造 `schemaVersion: 1`、8 数组、`counts` 8 键、checksum 基于 8 数组计算的信封；
- 导入到空 v2 库：`migratedFrom === 1`；
- 8 表行数恢复（`meta` 多 1 行 `lastImportedAt`，符合导入动作语义）；
- 3 张长期任务表为空；
- 全部任务 `deletedAt === null`；
- 日志的 `taskId` 引用保持。

这等价于 R1 路径「删库 → 装回 v1 数据」，只是把浏览器操作换成了数据层调用。

### D. v2 备份往返

- 升级后把一行任务软删除（`deletedAt` 写入时间戳）；
- 导出：`schemaVersion === 2`、`counts` 为 11 键；
- 导入空库：`migratedFrom === null`、`counts.tasks === 2`、软删除行的 `deletedAt` 原值保留。

验证了设计 §11 的核心承诺：**备份不隐藏软删除，恢复不过滤 `deletedAt`**。

## 5. T12 手工演练：未执行，原因与替代

设计 §15 的 T12 要求「rescue 导出 → 删库 → v1 导入」的手工/集成演练。本轮**没有执行**，三个客观原因：

1. 新版工程内**不存在 rescue 工具**（`public/tools/` 为空），设计中的 X1「只读救援页」尚未实现；
2. 本阶段沿用全程约束：**不启动服务、不访问真实 IndexedDB、不触碰浏览器 profile**；
3. 「删库」动作属于不可逆操作，在没有 rescue 工具的前提下无法保证「先导出再删」。

因此本轮用 §3 的 A–D 覆盖了同一组状态迁移的数据层部分，并给出下面的人工清单，待你单独授权（或先批准实现 rescue 工具）后在真实浏览器执行：

1. 用旧版接口导出 v1 JSON，记录 `counts`；
2. 打开新版（4180），确认自动升级，核对 11 表与 C1–C9；
3. 用 rescue 工具再导出一次（v2），与第 1 步的 8 表计数比对；
4. 在 DevTools → Application → IndexedDB 删除 `daily-schedule-lite`；
5. 重新打开新版（空库），导入第 1 步的 v1 备份，确认 `migratedFrom=1`、8 表恢复、3 张新表为空；
6. 导入第 3 步的 v2 备份，确认 11 表完整、软删除与历史保留。
