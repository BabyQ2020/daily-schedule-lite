## 4. 聚合组装方式

```
1) 取本页主记录（longTasks）
2) ids = 本页 taskId[]
3) versions  = longTaskRuleVersions.where('taskId').anyOf(ids).toArray()
4) exceptions= longTaskExceptions.where('taskId').anyOf(ids).toArray()
5) 按 taskId 分桶（Map）
6) 每条主记录组装 {task, versions, exceptions, issues}
```

- **固定 2 次批量查询**，与任务数无关（测试 `F. 批量查询同样是单事务 + 两次批量读` 用 spy 断言各调用 1 次）。
- 空 ids 在进入事务前直接返回 `[]`（`getLongTaskAggregates` 首行），不调用 `anyOf([])`。
- `getLongTaskAggregate` 单条路径使用 `where('taskId').equals(id)`。
- 批量结果**严格按输入顺序**：先按唯一 id 顺序 `bulkGet` 主记录，跳过不存在者，再按该顺序组装。

## 5. 事务读取方式

三个接口都在同一个只读事务内完成：

```ts
database.transaction(
  'r',
  [database.longTasks, database.longTaskRuleVersions, database.longTaskExceptions],
  async () => {
    /* 读主记录 + 两次批量读 + 组装 */
  },
);
```

- 事务范围：3 张表；模式 `'r'`。
- 分页发生在组装之前：先过滤/排序/分页主记录，再只为该页 ids 读取关联表（`E. 每页只查询本页主记录的关联数据`）。
- **单个聚合内部不截断**：`E. 单个聚合的 versions / exceptions 不被分页截断` 用 25 个版本 + pageSize 1 验证仍返回 25 条。

## 6. 排序与过滤实现

| 对象     | 规则                                                                               |
| -------- | ---------------------------------------------------------------------------------- |
| 聚合列表 | 默认 `updatedAt desc`；`startDate`/`priority`/`title` 可选；同值统一 `id asc` 兜底 |
| 规则版本 | `effectiveFrom` 升序 → `versionNo` 升序 → `id` 升序                                |
| 例外     | `occurrenceDate` 升序 → `revision` 升序 → `id` 升序                                |

过滤：`deleted`（默认 active，`'deleted'` 走 `where('deletedAt').above('')` 索引）、`archived`（默认 active，内存过滤，因无索引）、`priorities`、`tagId`、`startFrom/startTo`、`keyword`（标题+描述+备注，大小写不敏感子串）。

候选集来源优先级：`tagId` 索引 → 单一 `priority` 索引 → `startDate` 区间索引 → `deleted` 非空索引 → 全表。无法索引时整表扫描（长期任务量级小）。

## 7. issues 识别规则

| code                          | 触发条件                                                                                   | 是否修复             |
| ----------------------------- | ------------------------------------------------------------------------------------------ | -------------------- |
| `NO_VERSIONS`                 | 主记录存在但 `versions` 为空                                                               | 否                   |
| `VERSION_ORDER`               | 按 `effectiveFrom` 排序后，`versionNo` 未严格递增                                          | 否（不重排、不改号） |
| `EXCEPTION_REVISION_GAP`      | 同一日期内 revision 区间有空洞（如 1、3）                                                  | 否（不补记录）       |
| `EXCEPTION_PREVIOUS_MISMATCH` | `revision=1` 却有前序；或 `revision>1` 的 `previousRevisionId` 不等于 revision-1 记录的 id | 否（不改链）         |
| `EXCEPTION_ORPHAN_BASE`       | 同一日期最小 revision > 1（缺基础记录）                                                    | 否（不补 v1）        |

- 每个（任务、日期）最多各报 1 条，避免刷屏。
- 未新增「重复 revision / 重复 versionNo / 重复 effectiveFrom」类 issue：这三类由 DB 唯一索引兜底，正常写入无法产生，读取层再判断属于死代码（与授权「不要为了理论状态增加无逻辑类型」一致）。

## 14. 遗留风险

1. `archivedAt` 无索引，归档过滤为内存扫描；长期任务量级可接受，S5 若需优化要升 v3（本轮禁止）。
2. `NO_VERSIONS` 聚合会被返回而不是抛错，调用方（S3 Service）必须显式处理 `issues`，否则会当成「空安排」。
3. `getLongTaskAggregate` 不按删除/归档过滤，与 `getTask` 一致；若调用方误当「有效任务」使用需自行判断。
4. `VERSION_ORDER` 只检查 `versionNo` 是否随 `effectiveFrom` 严格递增，不检查是否从 1 连续（跳号本身不改变生效语义，且可能来自合法的历史导入）。
5. 空 `ids` 的短路是接口契约的一部分，未来若改成 `anyOf([])` 需重新验证 Dexie 行为。
