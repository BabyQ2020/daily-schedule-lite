## D. reopened 与 `effectiveFrom` 的时间语义

### D.1 案例

- 2026-05-01：`reopened`；
- 2026-05-05：新规则版本 v2 `effectiveFrom`；
- 2026-05-01 ~ 05-04：尚未到 v2 生效日。

### D.2 当前引擎的实际行为（方案 A）

`computeSlots` 按版本分段：v1 段止于 `v2.effectiveFrom - 1 = 05-04`（`schedule.ts:343-397` 的 `segTo` 计算），而 `endedGapsOf` 的区间是 `[ended, reopened)`，`05-01` 已闭区间结束，因此 **05-01 ~ 05-04 由 v1 继续生成**。

即当前实现 = 方案 A。这一行为不是巧合，而是"版本不可变 + 结束区间半开"两条规则的直接推论。

### D.3 三方案比较

| 维度 | A. 继续用上一版 | B. 恢复但不生成（空窗） | C. 强制 reopened = 新版本生效日 |
| --- | --- | --- | --- |
| 符合 Q1「ended 当天停止」 | 是（[ended, reopened) 半开，reopened 当天恢复） | 是 | 是 |
| 规则版本不可变 | 是（不造伪版本） | 是 | 是（但 UI 强制同时写版本，操作变重） |
| count 累计 | 连续、无歧义 | 空窗期不计次 → count 语义需新增"跳过区间"概念 | 连续 |
| 历史槽位影响 | 无（只影响未来） | 无 | 无 |
| 暂停区间交互 | 与暂停区间正交，可叠加 | 需新增"无规则区间"与暂停区间的优先级规则 | 正交 |
| 重复/漏生成 | 无重复；可能产生"用户以为不会再执行"的槽位 | 无重复、但存在无安排空窗 | 无重复 |
| 实现与测试成本 | 0（已实现） | 高（新状态 + count 规则 + 迁移语义） | 中（UI 约束 + 校验联动） |

### D.4 推荐：方案 A

理由：

1. **与已冻结的四项决策完全一致**：ended 当天停止、重新启用使结束边界失效、版本不可变、count 系列级累计；A 不需要任何新增状态。
2. **不会静默改写历史**：05-01 之前的历史槽位不受影响；05-01~05-04 属于"重新启用后的未来"，可以被规则覆盖。
3. **可解释**：用户看到的是"结束前用旧规则，改规则后按新规则"，中间不存在无法命名的"无规则状态"。
4. **成本最低**：现有引擎即 A，S3 只需把该语义写进服务层契约与提示文案。

**需要注意的体验风险**：重新启用后到新版本生效前，旧规则会短暂恢复。缓解：重新启用对话框展示"05-01 ~ 05-04 将按原规则执行（每天）"的预览；`upcomingSlots` 现有能力足以生成该预览。

### D.5 是否需要用户决策

**需要**：设计 §8.4 只写了"5 步计算顺序"，未逐字写明该间隔段用哪一版。建议把方案 A 写入 §8.4 作为一句显式规则（**文档改动，非代码**）。

标记：**DECISION-1（待用户确认后写入冻结文档；不改变 Q1–Q4 任何一项）**。

核对结论：

4. 不存在"stores 声明字段与实体字段不一致"：实体为嵌套对象，Dexie 只索引标量字段，`events`/`milestones` 等内嵌结构无需声明。

### E.2 `tasks.deletedAt` 回填

必须与索引创建在**同一个 versionchange 事务**内完成：

```js
this.version(1).stores(STORES_V1); // 保留旧声明，保证 v1 库可升级
this.version(2)
  .stores(STORES_V2)
  .upgrade((tx) => tx.table('tasks').toCollection().modify((task) => {
    if (task.deletedAt === undefined) task.deletedAt = null;
  }));
```

要点：

- 只加索引不回填在技术上可运行（缺失字段不进索引），但会产生 `undefined` 与 `null` 两种表示，读取路径易误判（§4.1 已论证），因此**必须回填**。
- `modify` 逐行写入会触发索引更新，确保回填后 `deletedAt` 索引与数据一致。
- 回填只改 `deletedAt`，不得触碰其他字段。
- 升级失败 → 事务整体回滚，库保持 v1，可重试（§12.1）。

### E.3 升级隔离

- 只打开 `daily-schedule-lite`（`db.ts:16`）；代码库中不存在 `personal-workbench` 的打开路径（隔离扫描 0 命中）。
- `blocked` / `versionchange`：S1 需在打开失败时给出"请关闭其他标签页后刷新"的明确提示；不得自动强制升级。
- 不做半迁移：只允许单个 `versionchange` 事务完成。

### E.4 S1 验收（对应 §14）

- C1 11 表名称完全匹配；C2 `tasks` 计数不变；C3 每行 `deletedAt` 有值；C4 其余 7 表计数不变；C5 新 3 表为 0；C6 每个索引 `where().first()` 不抛错。

**结论：S1 具备实施条件。** 唯一前置是 E.1 的 stores 字符串在实施时逐字复核（本报告已给出可执行草案）。

## F. P3.2-S5 备份兼容实施条件

### F.1 当前实现 vs 设计目标

| 项 | 当前 | v1.2 目标 | 位置 |

### F.2 风险点（按严重度）

1. **顺序缺陷**：当前 counts 在 checksum 之前。扩到 11 表后，v1 备份（8 数组）会在 `countsOf` 抛 `TypeError`（`data[table]` 为 undefined），表现为"读取崩溃"而非"版本不兼容"的清晰提示。**必须按 §11.3 调整顺序**。
2. **schema 分派缺失**：zod 校验固定 8 数组，v1 备份能过、v2 备份缺数组会被误报为字段缺失；而 v2 缺数组应给出"文件不完整"的明确错误。
3. **checksum 计算时机**：必须对**原始 data** 计算；先补 `[]` 会必不匹配（v1.2 已修正，代码尚未体现）。
4. **v1 兼容路径**：v1 备份 `counts` 只有 8 键，比对时缺的 3 表按 0 处理，不能报"声明缺失"。
5. **deletedAt 保留**：恢复不得按 `deletedAt` 过滤，不得重置为 null。
