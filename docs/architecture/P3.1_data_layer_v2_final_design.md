## 4. 十一张表完整定义

通用约定：时间戳为 ISO 字符串，日期为 `YYYY-MM-DD`；`deletedAt=null` 表示未删除；**IndexedDB 合法键不含 null**，故 `deletedAt` 索引只包含已删除行（与 `db.ts:41-42` 对 `archivedAt` 的取舍一致）。

### 4.1 `tasks`（保留，新增 `deletedAt`）

| 字段 | 类型 | 空 | 默认 |
| --- | --- | --- | --- |
| id | string | 否 | — |
| title / description / note | string | 否 | `''`（title 必填） |
| projectId | string \| null | 是 | null |
| status | `todo|doing|done|cancelled` | 否 | todo |
| priority | `low|medium|high|urgent` | 否 | medium |
| planDate / dueDate | ISODate \| null | 是 | null |
| completedAt | string \| null | 是 | null |
| parentId | string \| null | 是 | null |
| tags | string[] | 否 | [] |
| archivedAt | string \| null | 是 | null |
| **deletedAt** | **string \| null** | **是** | **null** |
| createdAt / updatedAt | string | 否 | — |

索引：原 14 项全部保留，**追加 `deletedAt`**；不加 `[deletedAt+updatedAt]`（复合索引同样跳过 null 行，对活动列表无益）。

**v1 → v2 的历史记录兼容（技术审查 A，结论：必须回填）**

1. 旧行没有 `deletedAt` 属性；IndexedDB 建索引时缺失字段的行**不会进入索引，也不会报错**，所以"只加索引不回填"在技术上可运行。
2. 但两种表示（`undefined` 与 `null`）会让读取路径出现 `task.deletedAt ?? null` 的分支，且 `db.ts` 的 `Task` 类型要求该字段存在；一旦有代码直接用 `=== null` 判断就会误判。
3. 因此选择**在升级事务内回填**：
   ```ts
   await tx.table('tasks').toCollection().modify((task) => {
     if (task.deletedAt === undefined) task.deletedAt = null;
   });
   ```
   10k 行量级实测应在数百毫秒内（P3.2 用 fake-indexeddb 压测确认）；升级事务失败会整体回滚。
4. 回填后：活动查询 = 按索引查询后内存过滤 `deletedAt === null`；回收站查询 = `where('deletedAt').above('')`（合法键中 `''` 最小，非空字符串都在其后）。
5. 升级后核对 C3：每行 `deletedAt` 不是 `undefined`。

### 4.9 `longTasks`（新增，聚合根）

```ts
interface LongTaskRecord {
  id: string;
  title: string;
  description: string;
  note: string;
  priority: TaskPriority;
  startDate: ISODate;
  endDate: ISODate | null;
```

**软删除语义（Q3 已确认）**

- 删除只更新聚合根 `deletedAt`，**不动** `longTaskRuleVersions` 与 `longTaskExceptions`。
- 已软删除任务不参与日程展示、不参与 `computeSlots`、不进入"未来 5 次"。
- 恢复只清 `deletedAt`，保留全部版本、例外链、生命周期历史；**恢复 ≠ 重新启用**（见 10.4）。
- 已暂停/已结束的任务**允许**软删除；删除不改变生命周期事件，恢复后状态仍由事件推导。

### 4.10 `longTaskRuleVersions`（新增，只追加）

```ts
interface LongTaskRuleVersionRecord {
  id: string;
  taskId: string;
  versionNo: number;          // 1..N 连续
  effectiveFrom: ISODate;     // 严格递增
  spec: RecurrenceSpec;
  changeNote: string | null;
  createdAt: string;
}
```

索引：`id, taskId, effectiveFrom, &[taskId+effectiveFrom], &[taskId+versionNo]`（**Q2 已确认两个唯一索引同时生效**）。

约束与实现：

1. 同 taskId 下 `versionNo` 不重复（唯一索引）。
2. 同 taskId 下 `effectiveFrom` 不重复（唯一索引）。
3. `versionNo` 必须从 1 连续递增：由**服务层在事务内**取 `max(versionNo)+1` 计算，`validateLongTask` 的 A9 再校验顺序。
4. 追加时不允许调用方指定 versionNo（签名里没有该参数），避免跳号。
5. 并发追加：两个事务各自读到最后版本 N，都尝试写 N+1 → 第二个撞 `&[taskId+versionNo]`，抛 `ConstraintError` → 服务层翻译为 `ConflictError('规则版本已被其他窗口更新，请刷新后重试')`。
6. 冲突报告：Dexie 的 `ConstraintError` 不携带索引名，因此服务层在**捕获后重新读取链**判断是 `effectiveFrom` 重复（提示"该日期已有版本"）还是 `versionNo` 冲突（提示"请刷新重试"）。
7. 历史版本**不得 UPDATE/DELETE**（除彻底删除任务时的级联删除）。

### 4.11 `longTaskExceptions`（新增，只追加）

```ts
interface LongTaskExceptionRecord {
  id: string;
  taskId: string;
  occurrenceDate: ISODate;
  revision: number;                 // 1..N 连续
  previousRevisionId: string | null;
  changeKind: 'initial' | 'correction' | 'revocation';
  baseOccurrence: BaseOccurrence;
  before: ExceptionState;
  after: ExceptionState;
  reason: string | null;            // correction/revocation 必填
  createdAt: string;
}
```

索引：`id, taskId, occurrenceDate, [taskId+occurrenceDate], &[taskId+occurrenceDate+revision]`。

约束：

- 唯一索引防重复修订号；`previousRevisionId` 无数据库约束，靠"事务内重读链尾 + E15 + 唯一索引"三道防线。
- 链完整性由 `validateExceptionChain`（E4–E8）校验，用于导入/诊断。
- 撤销 = 追加 `revocation`；不物理删除单条。彻底删除任务时级联删除全部例外。

```ts
  expectedUpdatedAt: string,
  database?: WorkbenchDatabase,
): Promise<void>;
export function purgeLongTask(
  id: string,
  database?: WorkbenchDatabase,
): Promise<{ versions: number; exceptions: number }>;
```

硬约束：仓储只做 I/O 与约束兜底，不做业务判断；`updateLongTaskFields` 乐观锁（`expectedUpdatedAt` 不一致抛 `ConflictError`）；仓储不导出表对象。

### 6.2 Application Service（聚合根边界）

```ts
// src/services/long-tasks/service.ts（P3.2 新建）

```

写入协议（固定顺序，不可调换）：

1. 开事务（表范围见第 7 章）。
2. **事务内重新读取**聚合（不接受调用方传入的旧 versions/exceptions）。
3. 计算 `today`（注入或系统时钟）。
4. 运行守卫（`validateLongTask` + 对应写入门禁）。
5. 计算新记录的 id / versionNo / revision / previousRevisionId（**事务内计算**）。
6. 插入 + 更新 `longTask.updatedAt`（乐观锁校验）。
7. 提交；`ConstraintError` → 翻译为具体领域错误（第 4.10 节）。

**事务状态约束**：`ConstraintError` 表示该 `rw` 事务已被 IndexedDB 中止，**不能**在原事务内继续读链（会得到 `TransactionInactiveError`）；冲突识别必须在事务外新开**只读事务**完成。完整规则见第 24.2 节。

## 7. 事务边界（逐操作）

统一约定：写操作一律 `database.transaction('rw', [相关表], fn)`；读操作不加事务；`updatedAt` 为写入时刻。

| # | 操作 | 涉及表 | 事务 | 事务内校验 | 失败回滚 | 并发保护 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 创建普通任务 | tasks | rw | 新行校验 | 自动 | 无（新建） |
| 2 | 编辑普通任务 | tasks | rw | 读最新 + 乐观锁 | 自动 | `expectedUpdatedAt` |
| 3 | 普通任务软删除 | tasks | rw | 幂等（已删直接返回） | 自动 | 乐观锁 |
| 4 | 普通任务恢复 | tasks | rw | 幂等 | 自动 | 乐观锁 |
| 5 | 普通任务彻底删除 | tasks, dailyPlans, workLogs | rw | 重读引用后清理 | 自动 | 同事务一致 |
| 6 | 创建长期任务 | longTasks, longTaskRuleVersions | rw | 聚合校验 + versionNo=1 | 自动 | 新 id |
| 7 | 创建初始规则版本 | 同 6 | 与 6 同事务 | 同 6 | 同 6 | — |
| 8 | 新增规则版本 | longTasks, versions | rw | R0–R5 + 事务内 max+1 + 双唯一索引 | 自动 | `ConstraintError`→Conflict |
| 9 | 写入生命周期事件 | longTasks | rw | `validateLifecycleUpdate` | 自动 | 乐观锁 |
| 10 | 暂停 / 恢复 | longTasks | rw | `canPauseOn`/`canResumeOn` + 同日唯一 | 自动 | 乐观锁 |
| 11 | 结束 / 重新启用 | longTasks, versions | rw | `canEndOn`/`canReopenOn`；reopened 同事务追加新版本且 `effectiveFrom ≥ reopened.date` | 自动 | 双唯一索引 + 乐观锁 |
| 12 | 新增单次例外 | longTasks, exceptions | rw | `canExceptionOn` + E1/E3 + 事务内链尾 | 自动 | 唯一索引 |
| 13 | 撤销例外 | longTasks, exceptions | rw | 链尾存在、有原因、`after.mode='rule'` | 自动 | 唯一索引 |
| 14 | 再次 override | 同 12 | rw | 链尾存在、有原因、patch 非空 | 自动 | 唯一索引 |
| 15 | 长期任务软删除/恢复 | longTasks | rw | 幂等；**不级联** | 自动 | 乐观锁 |
| 16 | 长期任务彻底删除 | longTasks, versions, exceptions | rw | 三表级联 + 删除后无孤儿 | 自动 | 同事务 |
| 17 | 备份导出 | 11 表 | 只读事务 | 读取后重算 counts/checksum | 不写库 | 快照一致 |
| 18 | 备份恢复 | 11 表 | rw 单事务 | 10 步校验 + 条数核对 | 整体回滚 | 事务串行 |

补充：

- 一次事务只写一个聚合；批量操作逐聚合调用并汇总。
- 备份导出改为只读事务，避免"导出时数据被改"导致 counts 与 data 不一致（现状是 8 次独立读取，v2 一并修正）。
- 乐观锁的 `expectedUpdatedAt` 在事务内**重新读取后**比较，不能用调用方传入的旧值直接写。

## 8. 长期任务聚合一致性

### 8.1 聚合根边界

一个聚合 = 1 条 `longTasks` + N 条 `longTaskRuleVersions` + M 条 `longTaskExceptions`；所有写入经 `LongTaskService`，一次事务只改一个聚合。

### 8.2 只追加语义

规则版本只插入；例外只插入（撤销 = 追加 revision）；生命周期事件只追加（`created` 唯一）。

### 8.3 槽位身份与例外

槽位由 `(版本, 日期, slotIndex)` 决定；`slotIndex` 从系列起点累计，不因例外变化。`baseOccurrence` 记录写入当时的原始安排；规则变更导致某日不再是槽位时，已有例外成为"孤儿"——读取忽略并标记 `orphaned: true`，**不静默删除**。

### 8.4 `ended` / `reopened` 与规则版本区间（**Q1 + DECISION-1 已确认**）

**Q1 决策**：`ended.effectiveDate` 当天起不再生成执行安排。
**DECISION-1 决策（v1.3 新增）**：`reopened` 生效日早于下一条规则版本的 `effectiveFrom` 时，**两者之间继续沿用上一条有效规则版本**生成执行槽位；新版本不得提前生效。

| 情形 | 行为 |
| --- | --- |
| `ended.effectiveDate = 2026-11-10` | 2026-11-09 及以前正常生成；**2026-11-10 起不生成** |
| ended 当天是否消耗 count | **不消耗**（该日不产生槽位，`slotIndex` 不递增） |
| ended 后能否用普通版本恢复 | **不能**：普通 `appendRuleVersion` 不改变生命周期状态，`hardStop` 仍截断 |
| 重新启用 | 必须 `reopened` 生命周期事件 + 同一事务追加新版本，且 `effectiveFrom ≥ reopened.date`（可晚于，见 DECISION-1） |
| ended 作为生成上界 | `hardStop` 取 `ended - 1`，与 `endDate`、`until` 取最小值 |
| `reopened` 当天 | **恢复生成**；是否产出取决于当天是否匹配当时的有效规则、且不在暂停区间内 |
| 新版本 `effectiveFrom = reopened.date` | 当天**直接使用新版本** |
| 新版本 `effectiveFrom > reopened.date` | `[reopened.date, effectiveFrom - 1]` **沿用上一有效版本**；`effectiveFrom` 起用新版本（DECISION-1） |
| 新版本 `effectiveFrom < reopened.date` | 写入拒绝（R1/R5）：新版本不得早于重开日 |
| 版本提前生效 | 不允许：某日只能使用 `effectiveFrom ≤ 该日` 的版本 |
| 规则版本可变性 | 只追加、不可变；重开不回溯改写历史版本 |
| 重开后 count | **不重置**，继续从系列起点累计；间隔段的槽位照常计数 |
| ended 区间 | 半开区间 `[ended.date, reopened.date)`；ended 日不生成，reopened 日可生成 |
| 版本区间与生命周期 | **必须取交集**：`槽位 = { d | d 属于某版本段 ∧ d ∉ endedGaps ∧ d ∉ paused ∧ d ≤ hardStop }` |
| 与其它转换同日 | 违反 L1（同日最多一次转换），写入被拒绝 |

**上界与计算顺序（v1.3 修订为 7 步，固定不可调换）**：

1. `hardStop = min(endDate, until, ended - 1)`（三者均可为 null；均为闭区间；`ended - 1` 已是"最后一天执行"）。
2. `upper = min(dateUpper, hardStop)`；`upper < startDate` → 空结果。
3. 按版本分段：`segFrom = max(version.effectiveFrom, startDate)`，`segTo = min(下一版 - 1, upper)`；`segFrom > segTo` 跳过。
4. **生命周期交集**：逐日跳过 ended 区间（`endedGapsOf` 与 `hardStop` 双重保证）与暂停区间（`suspensionsOf`）。
5. `spec` 匹配 → 去重 → **入槽前**判 `count` 是否已满。
6. 例外状态最后应用（`skip` 计次不产出、`override` 只改展示字段、`revocation` 恢复原始规则）。
7. 查询窗口只在最后过滤（`slotsInRange` 先算到 `to` 再按 `from` 切片），**不影响 count**。

**为什么间隔段天然使用旧版本**：选版是 `activeVersionOf(versions, d) = max{ v.effectiveFrom ≤ d }`，与 `versionNo` 无关。reopened 后若新版尚未生效，逐日选版自然命中上一版，不需要额外分支，也不会"提前"用新版——05-01～05-04 命中 v1、05-05 起命中 v2 即该规则的结果。

**多次交替**：`hardStop` 只取"末尾没有后续 reopened 的 ended"（`endedOnOf`），历史 ended 由 `endedGapsOf` 的分段区间处理，**绝不会**用最早的 ended 永久截断。完整时间轴示例见第 24.1 节；DECISION-1 的间隔段示例与断言见第 25 章。

### 8.5 规则变更后的历史解释

- 历史槽位由"当天生效版本"解释，新版本不回溯。
- 例外绑定 `occurrenceDate + baseOccurrence.versionId`，版本变更不重写历史例外。
- count 系列级累计，不因版本或暂停重置（暂停不计次，skip 计次）。
- **reopened 间隔段**（`[reopened, 新版本 - 1]`）由上一有效版本解释；该段的槽位与例外归属上一版，不因后续追加版本而改写（DECISION-1）。
- 规则切换后，历史例外仍按 `(occurrenceDate, baseOccurrence.versionId)` 解释；版本区间变化不得触发例外重写或删除。

## 9. 生命周期与例外链设计

### 9.1 生命周期事件

`created` 唯一且 `date=startDate`；transitions 严格递增、同日最多一条、首个 ≥ created；`paused→resumed` 半开区间；`ended` 形成 `[ended, reopened)` 空档；状态由 `deriveState(task, today)` 推导，不落库。

`reopened` 写入时必须同事务追加一条 `effectiveFrom ≥ reopened.date` 的新版本（R5）。该版本可以**晚于** reopened：`[reopened, effectiveFrom - 1]` 沿用上一有效版本（DECISION-1），新版本从 `effectiveFrom` 生效。`reopened` 不重置 count，也不使 ended 区间内的任何日期重新成为槽位。

### 9.2 例外链

同一 `(taskId, occurrenceDate)` 下 revision 从 1 连续递增，`previousRevisionId` 指向上一条；有效状态 = 最大 revision 的 `after`；`revocation.after` 必须 `{mode:'rule'}`；`correction` 必须带原因并记录 `before`。

### 9.3 写入算法

```
writeException(taskId, date, changeKind, after, reason):
  tx:
    agg = readAggregate(taskId)
    chain = agg.exceptions where date, sorted by revision
    latest = chain.at(-1)
    revision = (latest?.revision ?? 0) + 1
    previousRevisionId = latest?.id ?? null
    before = latest ? latest.after : { mode: 'rule' }
    validateExceptionWrite({...})
    insert(record, baseOccurrence = slotOn(剔除该日例外后的聚合, date).base)
    touch(taskId)
```

## 10. 删除、恢复与归档

| 概念 | 字段 | 语义 | 默认列表 | 参与统计/生成 |
| --- | --- | --- | --- | --- |
| 归档 | `archivedAt` | 搁置/完成，保留历史 | 否 | 项目进度排除（现有） |
| 暂停 | `paused` 事件 | 暂不生成安排 | 是（显示暂停中） | 不生成 |
| 结束 | `ended` 事件 | 终止系列 | 是（显示已结束） | 不生成 |
| 软删除 | `deletedAt` | 回收站，可恢复 | 否 | 排除 |
| 彻底删除 | 物理删除 | 不可恢复 | 否 | 排除 |

### 10.1 优先级

`deletedAt` > `archivedAt` > 生命周期状态。

### 10.2 回收站

- 查询：`tasks.where('deletedAt').above('')`；longTasks 同理。
- 查看：回收站页两个 Tab（普通任务 / 长期任务），显示删除时间与原状态。
- 恢复：置 `deletedAt = null`；`archivedAt` 保留原值。

### 10.3 彻底删除

- 普通任务：沿用 `deleteTasks`（摘除 `dailyPlans.taskIds`、`workLogs.taskId→null` + 快照）。
- 长期任务：同事务删 `longTasks` + 该任务全部 `versions` + `exceptions`；返回删除条数；事务内检查 `versions/exceptions` 中不存在该 `taskId` 之外的孤儿（按本次 id 过滤核对）。
- 必须二次确认（Q3 已确认）。

### 10.4 恢复 ≠ 重新启用

- 恢复：仅清 `deletedAt`。若删除前是 `ended`，恢复后仍是 `ended`；若删除前是 `paused`，恢复后仍是 `paused`（打开即"暂停中"）。
- 重新启用：必须走 `reopened` 生命周期事件 + 新规则版本，受第 8.4 节约束。
- 已暂停/已结束任务允许软删除；删除不追加生命周期事件。

- 单事务覆盖 11 表：`clear()` → `bulkAdd`（settings/meta 用 `bulkPut`）→ 逐表核对条数 → 失败整体回滚。

## 12. v1 → v2 升级策略

### 12.1 升级动作

1. `DB_VERSION` 1→2、`SCHEMA_VERSION` 1→2。
2. `version(2).stores(11 表全量)`。
3. `upgrade(tx)`：只回填 `tasks.deletedAt`（第 4.1 节），不创建 longTask 行。
4. 升级在单个 `versionchange` 事务内；失败由 IndexedDB 回滚整个版本变更，库仍为 v1，可重试。

### 12.2 为什么不需要迁移旧数据

用户已确认不迁移旧工程 `personal-workbench` 数据、不做 v1 数据备份迁移【已确认 m03751】。v2 只处理新版库内已有 8 表数据。

### 12.3 升级前

- 强制建议导出 v1 JSON；用户拒绝也可升级，但 UI 必须提示"升级后旧版应用无法读取本库"。

### 12.4 降级

IndexedDB **不支持降低版本号**，不存在"原地 v2→v1"。

| 路径 | 步骤 | 代价 |
| --- | --- | --- |
| R1 回到 v1 应用 | 关闭所有标签页 → 删除数据库（或 rescue 导出后手动删）→ 打开 v1 → 导入升级前的 v1 备份 | 丢失升级后新增数据 |
| R2 回到上一份 v2 数据 | 用 v2 备份覆盖恢复 | 丢失导出后的增量 |

v2 备份不能喂给 v1 应用（schemaVersion 2 被拒），所以"升级前 v1 备份"是唯一回退凭据。

## 21. 最终决策记录（Q1–Q4）

### 21.1 Q1：ended 当天起停止（方案 A）

**决策原文**：`ended` 的 `effectiveDate` 当天起不再生成执行安排（11-09 及以前正常，11-10 起停止）。

落地要求（逐条对应）：

| # | 要求 | 落地位置 |
| --- | --- | --- |
| 1 | 当天不产生执行槽位 | `computeSlots` 的 `endedGaps` + `hardStop-1`（现状已如此） |
| 2 | 当天不消耗 count | 当天不进入循环，`slotIndex` 不递增 |
| 3 | ended 作为 hardStop | `hardStopOf = min(endDate, until, ended-1)` |
| 4 | 历史槽位与例外保留 | 只影响 `date ≥ ended` 的生成；不写历史 |
| 5 | 不得用普通版本恢复 | `appendRuleVersion` 不改 events，`hardStop` 仍截断 |
| 6 | 重开必须 lifecycle + 新版本 | `addLifecycleEvent('reopened')` 同事务追加版本，`effectiveFrom ≥ reopened.date` |
| 7 | 重开不重置 count | `slotIndex` 从系列起点连续累计 |
| 8 | 与 until/endDate/count 共存 | 第 8.4 节固定 7 步顺序（v1.3） |
| 9 | 同日多转换 | L1 拒绝 |

数据与测试影响：无新字段；`schedule.test.ts` 补 T16 的 10 例（含"ended 当天不计数""重开不重置""与 until 取小"）。

### 21.2 Q2：双唯一索引

- 索引：`&[taskId+effectiveFrom]` + `&[taskId+versionNo]`。
- `versionNo` 从 1 连续；服务层在事务内 `max+1`；调用方不可指定。
- 并发：唯一索引兜底，`ConstraintError` 翻译为 `ConflictError`；捕获后重读链判断冲突类型（日期重复 / 版本号冲突）。
- 历史版本禁止 UPDATE/DELETE（除级联彻底删除）。

### 21.3 Q3：软删除与回收站

- 只更新聚合根 `deletedAt`；不动 versions/exceptions/events。
- 删除后不展示、不生成槽位、不进入未来 5 次。
- 回收站可查看、可恢复；恢复只清 `deletedAt`，保留历史与 `archivedAt`。
- 已暂停/已结束允许软删除。
- 恢复 ≠ 重新启用（10.4）。
- 彻底删除：二次确认 + 单事务三表级联 + 孤儿检查。

### 21.4 Q4：备份保留已删除长期任务

- 导出不过滤 `deletedAt`；counts 含已删除。
- 恢复保留原 `deletedAt`。
- 引用校验覆盖 `versions.taskId`、`exceptions.taskId`、`previousRevisionId` 链、每日 revision 连续性。
- 链断裂拒绝恢复，不静默丢弃。

### 21.5 DECISION-1：reopened 与规则版本的间隔（v1.3 新增，用户已确认）

**决策原文**：当 `reopened` 生效日期早于下一条规则版本的 `effectiveFrom` 时，两者之间**继续沿用上一条有效规则版本**生成执行槽位。

| 日期 | 事件 | 执行规则 |
| --- | --- | --- |
| 2026-04-06 | `ended` | 当天起停止执行 |
| 2026-05-01 | `reopened` | 恢复执行 |
| 2026-05-01～05-04 | 尚无新版本生效 | **沿用上一条有效规则版本** |
| 2026-05-05 | 新版本 `effectiveFrom` | 开始使用新规则版本 |

不变更的四项既有决策：Q1（ended 当天起停止）、Q2（双唯一索引）、Q3（软删除进回收站）、Q4（备份保留已删除与全部历史）。

- 生效条件：新版本 `effectiveFrom ≥ reopened.date`；等于则当天用新版，晚于则中间沿用旧版；早于则写入拒绝。
- 计数：`reopened` 不重置 count；间隔段照常累计，暂停与 ended 日不计数。
- 生命周期：`ended` 区间仍为半开 `[ended.date, reopened.date)`；ended 日不生成，reopened 日可生成（若匹配当时规则）。
- 历史：规则版本不可变；间隔段的槽位与例外归属上一版，后续追加版本不改写。
- 取交集：版本段必须与生命周期区间取交集，ended 区间内**不得**生成槽位。
- 代码现状：引擎 `activeVersionOf` 按日期选版，天然满足本决策；但三表与 Service 层仍未实现，故本决策当前只体现在设计与测试计划（T22）。

## 24. 补充技术核查（P3.1-Final-Review）

### 24.1 R1：多次 `ended` / `reopened` 的时间轴

#### 24.1.1 结论

**当前设计（引擎实现）是正确的**，依据是三条互相独立的机制，而不是"取最早 ended"：

| 机制 | 源码位置 | 作用 |
| --- | --- | --- |
| `endedOnOf(events)` | `schedule.ts:179-186` | 顺序扫描：遇 `ended` 记日期，遇 `reopened` 清空；因此只保留**末尾没有 reopened 的 ended** |
| `endedGapsOf(events)` | `schedule.ts:192-207` | 逐个 `ended→reopened` 生成半开区间 `[ended, reopened)`；末尾无 reopened 的记 `[ended, null)` |
| `isEndedOn(gaps, date)` | `schedule.ts:209-213` | 循环内逐日判断，命中即跳过（不占 count） |

`hardStopOf = min(endDate, until, ended-1)`（`schedule.ts:224-229`）只使用 `endedOnOf` 的结果；**历史 ended 不会被当作永久上界**。

#### 24.1.2 构造的时间轴（两次 ended、两次 resumed/reopened）

| # | 日期 | 事件 / 配置 | 说明 |
| --- | --- | --- | --- |
| 1 | 2026-01-05（周一） | `created`；`startDate`；规则 **v1 = 每天**；`endCondition = count(60)` | 系列起点 |
| 2 | 2026-01-20 | `paused` | 暂停区间 `[01-20, 01-25)` |
| 3 | 2026-01-25 | `resumed` | 恢复 |
| 4 | 2026-02-10 | `ended`（第一次） | 结束区间 `[02-10, 03-01)` |
| 5 | 2026-03-01 | `reopened` + 规则 **v2 = 每周一、三**（`effectiveFrom=03-01`） | 重开必须同事务追加新版本 |
| 6 | 2026-04-06 | `ended`（第二次） | 结束区间 `[04-06, 05-01)` |
| 7 | 2026-05-01 | `reopened` + 规则 **v3 = 每天**（`effectiveFrom=05-01`） | 第二次重开 |
| 8 | — | `endDate=null`、`until=null` | 无其他上界 |

`endedOnOf` 扫描结果：`ended`(02-10) → `reopened`(03-01) 清空 → `ended`(04-06) → `reopened`(05-01) 清空 → **返回 null**，因此 `hardStop=null`。

| 段 | 日期范围 | 规则 | 排除 | 槽位数 | 累计 |

具体槽位：

- A：`01-05 … 01-19`（15 天）
- B：`01-25 … 01-31`、`02-01 … 02-09`

#### 24.1.4 逐项回答核查问题

| # | 问题 | 结论与依据 |

### 24.2 R2：`ConstraintError` 与事务状态

#### 24.2.1 IndexedDB 语义（结论先行）

1. 唯一索引冲突会让**产生该请求的事务 abort**；`ConstraintError` 是这次请求的错误，事务随后进入 abort 状态。
2. 在 `catch` 里捕获它**不会**让原事务恢复；原事务的下一次请求会抛 `TransactionInactiveError`。
3. 因此"捕获 ConstraintError 后在同一事务里重读链"是**错误设计**，v1.1 的表述过于简略，v1.2 在此修正。
4. 事务 abort 后，已写入的行全部回滚，不存在部分写入。

#### 24.2.2 三层职责（必须分开）

| 层 | 位置 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| ① 事务内 | `db.transaction('rw', …)` 回调 | 事务内重读聚合；**主动预检**（`effectiveFrom` 是否已存在）；算出 `max(versionNo)+1`；插入；更新根；发现业务冲突时**主动 throw `ConflictError`**（让事务 abort，携带精确文案） | 不捕获 `ConstraintError`、不吞错、不在事务内做诊断读 |
| ② 事务外诊断 | Service 的 `catch` 分支 | 判断错误名；新开**只读事务**（`db.transaction('r', versions, …)`）读取链尾；据此区分"日期重复"与"版本号竞争"；诊断本身失败时不掩盖原始错误 | 不写入、不复用已死事务、不无限重试 |
| ③ 返回调用方 | Service 出口 | 统一抛 `ConflictError`（含 `code` 与可操作提示）；UI 显示"请刷新后重试/换一个生效日期" | 不把 `ConstraintError` 原文透给 UI |

#### 24.2.3 参考流程（设计，非实现）

```ts
async function appendRuleVersion(taskId, input) {
  try {
    return await db.transaction('rw', [longTasks, longTaskRuleVersions], async () => {
      const agg = await readAggregateInTx(taskId);          // 事务内重读
      if (!agg) throw new NotFoundError('长期任务');
      const versions = agg.versions;
      if (versions.some((v) => v.effectiveFrom === input.effectiveFrom)) {
        throw new ConflictError('该日期已有规则版本，请选择其他生效日期。'); // 主动 abort
      }
      const nextNo = versions.length === 0
        ? 1
        : Math.max(...versions.map((v) => v.versionNo)) + 1;  // 事务内计算
      await longTaskRuleVersions.add({ ...input, taskId, versionNo: nextNo });
      await longTasks.update(taskId, { updatedAt: nowIso() });
      return nextNo;
    });
  } catch (error) {
    if (!isConstraintError(error)) throw error;
    // 原事务已 abort：只能在事务外新开只读事务诊断
    const reason = await diagnoseVersionConflict(taskId, input.effectiveFrom);
    throw new ConflictError(reason);
  }
}

async function diagnoseVersionConflict(taskId, effectiveFrom) {
  try {
    return await db.transaction('r', longTaskRuleVersions, async () => {
      const versions = await longTaskRuleVersions.where('taskId').equals(taskId).toArray();
      if (versions.some((v) => v.effectiveFrom === effectiveFrom)) {
        return '该日期已有规则版本，请选择其他生效日期。';
      }
      return '规则版本已被其他窗口更新，请刷新后重试。';
    });
  } catch {
    return '保存冲突，请刷新后重试。';   // 诊断失败不得掩盖原始冲突
  }
}
```

#### 24.2.4 并发与 versionNo

- 同一连接：Dexie 对相同表集合的 `rw` 事务**串行**执行，后一个事务的读发生在先一个提交之后，`max+1` 自然不同。
- 多标签页 / 多连接：IndexedDB 以事务为粒度加锁，`rw` 重叠范围仍串行；但"先读后写"跨事务时仍有竞态，因此：
  1. 一致性由**双唯一索引**兜底（`taskId+versionNo`、`taskId+effectiveFrom`）；
  2. 冲突由 `ConstraintError` 暴露并被翻译；
  3. 绝不使用"先读全局最大值、再在另一个事务写入"的两段式写法。
- 不会分配相同 versionNo 的最终保证顺序：事务串行 → 事务内 `max+1` → 唯一索引 → `ConflictError` 提示刷新。

#### 24.2.5 避免诊断本身引入新错误

- 诊断只用 `transaction('r', …)`，不写库，不触发 `ConstraintError`。
- 诊断不得在 `catch` 中 `await` 原事务的任何 promise（会抛 `TransactionInactiveError`）。
- 诊断失败时抛出原始错误的通用版本，不叠加二次异常。
- 事务回调内禁止 `await` 非 Dexie 的异步操作（会丢失 Dexie 事务 zone，导致事务提前提交）。

#### 24.2.6 用例（T20）

1. 事务内预检命中 → `ConflictError('该日期已有规则版本…')`，表中无新增行。
2. 构造 `ConstraintError`（绕过预检的并发写）→ 原事务 abort → 诊断返回"刷新后重试"→ 行数不变。
3. 诊断事务失败（模拟 DB 关闭）→ 抛通用 `ConflictError`，不抛 `TransactionInactiveError`。
4. 两个连接并发追加同 `effectiveFrom` → 一个成功、一个 `ConflictError`，`versionNo` 不重复。
5. 一次事务中第二步失败 → 第一步的插入被回滚（无残留）。
6. `bulkAdd` 触发冲突 → 整批回滚。

#### 24.3.5 用例（T21）

1. 用 v1 备份（8 表，无 `deletedAt`）导入 → 成功，任务数不变，`deletedAt` 全为 `null`。

## 25. DECISION-1 专章：reopened 与规则版本的间隔（v1.3）

### 25.1 规则清单

| # | 规则 | 依据 |
| --- | --- | --- |
| D1 | `reopened` 当天恢复执行；是否产出由当天有效规则与暂停状态决定 | §8.4、§9.1 |
| D2 | 新版本 `effectiveFrom = reopened.date` → 当天用新版本 | 选版 `activeVersionOf` |
| D3 | 新版本 `effectiveFrom > reopened.date` → `[reopened, effectiveFrom-1]` 用上一有效版本 | DECISION-1 |
| D4 | 新版本 `effectiveFrom < reopened.date` → 拒绝写入（R5） | 守卫 |
| D5 | 某日只能使用 `effectiveFrom ≤ 该日` 的版本，新版本不得提前生效 | `activeVersionOf` |
| D6 | 规则版本只追加、不可变；重开不改写历史版本 | §8.2、§4.10 |
| D7 | `reopened` 不重置 count；间隔段正常累计 | §8.4、§8.5 |
| D8 | ended 区间 `[ended, reopened)` 内不生成槽位；ended 日不计次 | Q1 |
| D9 | 版本段与生命周期区间必须取交集 | §8.4 第 4 步 |
| D10 | 间隔段的槽位与例外归属上一版，后续版本不改写 | §8.3、§8.5 |

### 25.2 计算流程（在 §8.4 的 7 步内如何落地）

```
for version in versionsSortedByEffectiveFrom:
    segFrom = max(version.effectiveFrom, task.startDate)
    segTo   = min(nextVersion ? nextVersion.effectiveFrom - 1 : upper, upper)
    if segFrom > segTo: continue
    for d in segFrom..segTo:
        if d > upper: break
        if isPausedOn(suspensions, d): continue      # 生命周期交集：暂停
        if isEndedOn(endedGaps, d): continue         # 生命周期交集：ended 区间
        if not matchesSpec(version.spec, d): continue
        if seen.has(d): continue                     # 多版本同日只取最早一段
        if countLimit !== null and slotIndex >= countLimit: return slots   # 入槽前判满
        slots.push({ date: d, slotIndex, versionId: version.id, ... })
        slotIndex += 1
```

关键点：本流程**不需要**为 DECISION-1 增加分支。`reopened` 只解除 ended 区间；版本仍按各自的 `[effectiveFrom, 下一版-1]` 分段。因此 `[reopened, 新版-1]` 区间天然只可能命中上一版（若上一版的 `effectiveFrom ≤ reopened`），新版只在 `d ≥ effectiveFrom` 时进入其分段。这正是"沿用上一有效版本"的实现方式。

### 25.3 构造示例与预期

时间轴：`startDate=2026-05-01（周五）`，v1 = 每天；`ended 05-10`；`reopened 05-20`；新版本 v2 = 每周一、三，`effectiveFrom=05-25`；`count=null`、`endDate=null`、`until=null`。

| 区间 | 规则 | 说明 |
| --- | --- | --- |
| 05-01～05-09 | v1 每天 | 9 个槽位 |
| 05-10～05-19 | 无 | ended 区间 `[05-10, 05-20)` |
| 05-20～05-24 | **v1 每天**（间隔段，DECISION-1） | 05-20、21、22、23、24 = 5 个槽位 |
| 05-25 起 | v2 每周一、三 | 05-25（周一）、05-27、06-01… |

断言：`slotsInRange(05-01, 05-31)` 中 05-20～05-24 **必须存在且标题/优先级来自 v1 的 baseOccurrence**；05-25 使用 v2；若错误地"reopened 后无新版本即不生成"，则会得到 11 个槽位而非 16 个。

### 25.4 测试用例（T22，9 例）

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | reopened 与新版本同日 | 当天使用新版本；无间隔段 |
