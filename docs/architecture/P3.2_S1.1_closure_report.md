## A. ReportsPage 测试问题：原因与修复方式

### A.1 现象

全量测试偶发失败：

```
TestingLibraryElementError: Found multiple elements with the text: /v2/
  at src/pages/ReportsPage.test.tsx:110
```

单文件运行 5/5 通过，全量运行偶发失败（S1 期间 3 次全量里 2 次失败）。

### A.2 原因

`ReportsPage.tsx` 中 `"v2"` 会同时出现在两处：

| 位置 | 文本 | 渲染时机 |
| --- | --- | --- |
| 编辑器头部 | `草稿 v2 · 自动生成` | 点击「重新生成」后由 `setBody(...)` **立即**更新 |
| 右侧版本记录 | 版本条目按钮 `v2 2026-11-19 18:52` | 由 `useLiveQuery` **异步**刷新 |

`findByText(/v2/)` 是纯文本匹配，一旦两处同时存在就抛 "Found multiple elements"；
而在 jsdom + 全量并行负载下，`useLiveQuery` 的刷新实测可迟到 **5–8 秒**，
若它迟到，则只剩编辑器头部一处，断言又会变成"匹配到错误对象"。

即：**失败原因是测试定位方式不稳定，而不是页面行为变化**——实测数据库已写入 v2
（`reports` 表 `[{version:2,isEdited:false},{version:1,isEdited:true}]`），
版本面板最终也正确列出 v2，只是时间不确定。

### A.3 修复方式（只改测试）

```ts
// 版本条目的可访问名以 "v2" 开头（"v2 2026-11-19 18:52"）；正文里也有 /v2/
//（"草稿 v2"），纯文本正则会同时命中两处，因此改用角色 + 前缀匹配。
// 版本列表由 liveQuery 异步刷新，jsdom + 并行负载下实测可迟到 5–8s，故放宽等待。
expect(
  await screen.findByRole('button', { name: /^v2\b/ }, { timeout: 15000 }),
).toBeInTheDocument();
```

- 由"整页文本匹配"改为 **角色 + 可访问名前缀匹配**，锁定右侧版本条目按钮；
- 等待时间放宽到 15s（只影响慢路径，不改变断言内容）；
- 原有断言全部保留：
  - `findByRole('button', { name: /^v2\b/ })`：v2 版本条目出现在版本记录中；
  - `waitFor(... versions.sort() === [1, 2] ...)`：旧版本仍保留在库中。
- 未删除任何断言、未跳过测试、未调整执行顺序、未屏蔽异常、未降低覆盖率；
- 未修改任何业务页面组件。
