## C. Version 1 → Version 2 升级实现

```ts
this.version(1).stores(V1_STORES);          // 老库必须能被识别，升级路径才成立
this.version(2)
  .stores(V2_STORES)                        // 11 表全量声明（漏写=删表）
  .upgrade(async (tx) => {
    await tx
      .table('tasks')
      .toCollection()
      .modify((task: { deletedAt?: string | null }) => {
        if (task.deletedAt === undefined) task.deletedAt = null;
      });
  });
```

要点：

1. **保留 v1 声明**（C2 前提）。删掉 `version(1)` 会让 Dexie 无法建立增量路径。
2. `V2_STORES` 用 `{ ...V1_STORES, tasks: v1 + ', deletedAt', ...3 表 }` 生成，避免手抄 14 个 tasks 索引时漏项。
3. 升级回调**只**用 `tx.table('tasks')`；`modify` 对全表游标生效，不分批、不跳过。
4. 回填条件为 `undefined` 才写 `null`，已存在有效 `deletedAt` 的行保持原值。
5. 回调内无 `await` 非 Dexie 异步、无网络、无计时器 → 符合 IndexedDB 事务限制。
6. 任一行抛错 → 整个 versionchange 事务 abort（C5 验证）。
7. 备份常量 `BACKUP_TABLE_NAMES` **保持 8 表**：备份格式属 S5，本轮不改（避免顺手扩大范围）。

## G. 失败回滚测试细节

构造方式：测试内定义 `FailingDatabase extends Dexie`，**使用与生产完全相同的 `V1_STORES` / `V2_STORES`**，但在 `version(2).upgrade()` 里先写入 `deletedAt='partial'`，再 `throw new Error('模拟升级失败')`。

断言链：

1. `await expect(failing.open()).rejects.toThrow()` —— 升级确实失败。
2. 关闭后用 `version(1)` 重新打开：`verno === 1` —— 未升到 v2。
3. `tasks` 两条记录 id 完整（`keep-1`/`keep-2`），且 `deletedAt === undefined` —— 部分写入被撤销。
4. `objectStoreNames` 长度 **8** 且不含 `longTasks` —— 新表未残留。
5. 重新打开后仍可正常读取 → 库处于一致状态。

**测试边界（必须说明）**：以上回滚语义由 fake-indexeddb 实现提供，**未在真实 Chrome/Edge 中验证**——本轮禁止启动服务、禁止访问真实 IndexedDB。真实浏览器对 versionchange 事务的 abort 语义有明确规范，但"已通过"仅指测试环境（见 J-2）。
